# Этап 05 — домен, АРМ, RADIUS + Squid, аналоги Secret Net

## Цель
Поднять контроллер домена (Samba AD DC), ввести АРМ в домен, настроить аутентификацию пользователей, RADIUS-авторизацию выхода в интернет и открытые аналоги функций Secret Net. Это самый хрупкий этап, действуй последовательно и фиксируй каждую проблему.

## Что сделать
1. **dc** (intra .20): Samba AD DC, домен `gis.local`, realm `GIS.LOCAL`, встроенный DNS Samba. Провизия через `samba-tool domain provision`. Если в контейнере мешает файловая система (xattr/ACL), используй named volume и/или `--use-xattrs=yes` и запиши. Пользователи и группы по документации ГИС (Admin: `sysadmin`, `secadmin`; Workgroup: `archhead`, `archstaff1`; Guest не нужен в домене). Парольная политика: `samba-tool domain passwordsettings set …` (длина, сложность, блокировка после неудачных попыток).
   - **Запасной вариант**, только если Samba AD не заработала после разумных попыток (запиши, что пробовал): MIT Kerberos + OpenLDAP. Тогда отступление запиши в PROGRESS и в результаты.
2. **arm1** (intra .31): Debian-клиент, DNS на dc, ввод в домен (`realm join`/`adcli` + `sssd`, либо winbind). Вход доменным пользователем (`getent passwd archstaff1`, `su - archstaff1`, `kinit`). PAM: блокировка при повторных неудачных входах (`pam_faillock`), проверка сложности паролей (`pam_pwquality`). Реальный sshd для этапа 04.
3. **radius** (transit .5): FreeRADIUS. Клиент: fw-int (общий секрет в `stand/secrets/`). Пользователи: файлом `users` (учебные учётки), если успеешь, то привязка к Samba (ntlm_auth) как дополнение.
4. **Squid на fw-int** (прокси на :3128 в intra): авторизация через RADIUS (`basic_radius_auth` или аналог; проверь, что он есть в пакете Debian). Это закрывает примечание схемы «выход в интернет только после авторизации на RADIUS». Политика fw-int: из intra наружу только через Squid.
5. **inet** (ext .80): простой веб-сервер, цель для проверки выхода в интернет.
6. **Аналоги функций Secret Net на arm1** (только открытое ПО, часть опциональна, если не хватает времени):
   - разграничение доступа: POSIX ACL на каталогах (`setfacl`), каталог отдела с доступом только группе Workgroup;
   - контроль целостности: AIDE (инициализация базы, изменение файла, обнаружение);
   - аудит входов и действий: логи PAM/sshd, auditd если запускается в контейнере (если нет, запиши ограничение);
   - антивирус: ClamAV (в паспорте варианта 3 он указан), проверка тестовым файлом EICAR (это безвредная стандартная тестовая строка);
   - аутентификация и парольная политика: доменные (Samba AD) и PAM.
7. **Минимальное логирование (примечание 8):** составь таблицу «узел → какие события пишутся → где лежит лог» (access/error web, Squid, FreeRADIUS auth, Samba, sshd, Suricata, счётчики nft). Покажи по одному примеру записи.
8. **Опционально GUI АРМ** (если останется время и пользователь подтвердит): Xfce + noVNC в контейнере arm1 на 127.0.0.1:6080 для живого показа рабочего стола. Если нет, пропусти и не трать на это время.

## Обязательные проверки (каждая со скрином)
- `dc`: `samba-tool domain info`, список пользователей и групп, политика паролей.
- `arm1`: ввод в домен успешен, `getent passwd`, вход доменным пользователем, неверный пароль несколько раз → блокировка (`faillock`).
- RADIUS: `radtest` с верными и неверными данными (Access-Accept / Access-Reject).
- Squid: arm1 → `curl -x http://192.168.200.1:3128 http://198.51.100.80` без учётки → 407; с неверной → 407; с верной (из RADIUS) → 200. Прямой выход arm1 в ext без прокси не проходит. Строки из `access.log` Squid и auth-лога FreeRADIUS.
- ACL, AIDE, ClamAV (EICAR): до/после, что сработало.
- Таблица логов (п. 7) с реальными примерами.
- Совместно с этапом 04: клиент через VPN заходит по ssh на arm1 доменным пользователем.
