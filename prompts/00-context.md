# Контекст проекта «Стенд ГИС»

## Цель
По схеме `docs/scheme-gis-auo.png` (ГИС «АУО», вариант 3: сайт Счётной палаты РФ) развернуть стенд на виртуализации. Здесь это Docker Compose. Настроить основные механизмы защиты и показать, что они работают. Потом результаты оформят в отчёт Word по образцу `docs/Курсовая Вариант выполнения 1.pdf`. Это делает не ты. Твоя задача: рабочий стенд, точные факты и реальные скрины в `results/`.

## Источники (`docs/`)
- `scheme-gis-auo.png`: главная схема (внешний МЭ → общий коммутатор → шлюз ДМЗ с МЭ+IDS/IPS → web, FTP; VPN-сервер; внутренний МЭ с RADIUS-клиентом → БД, контроллер домена, АРМ; удалённый клиент).
- `scheme-m2.png` / `СхемаМ2(1).vsd`: общая схема курса, нужны только её примечания (ниже).
- `variant3.md`: паспорт ресурса и решения группы.
- `Отчет_ГИС_1_анализ_документации.docx`: таблица узлов, меры защиты, пользователи (группы Admin/Workgroup/Guest).
- `Курсовая Вариант выполнения 1.pdf`: образец. Смотри, какие проверки он показывает: ping снаружи не проходит, сайт открывается, IDS пишет алерты на ICMP/HTTP/XSS, маршрутизация между зонами, домен, удалённый доступ.

## Решения группы
- На всех хостах Debian (stable, `debian:13`/trixie; если пакет недоступен, `debian:12`, это запишешь в отступления).
- Межсетевой экран: **nftables**. Защищённый канал: **WireGuard**. СУБД: **PostgreSQL**. Только открытое ПО.
- Замены относительно схемы: Astra Orel → Debian; pfSense → Debian + nftables + Squid; OpenVPN → WireGuard; Windows Server DC → Samba AD DC; Windows 10 АРМ → Debian-клиент; IDS/IPS → Suricata; Secret Net (Windows, платный) → открытые аналоги (см. этап 05).
- Примечания схемы М2: адресация статическая; узлы лёгкие; допустимо объединять сервисы; АРМ достаточно одного; ACL на МЭ можно не настраивать (для внешнего аудита), поэтому нужны два режима (`protect`/`audit`); выход во внешнюю сеть из внутренней только после авторизации на RADIUS; логирование хотя бы минимальное.

## Топология и адреса (обязательны; отступать только с записью в PROGRESS)
Все сети `internal: true`, статические адреса через ipam. Маршруты ставь явно в entrypoint (`ip route replace ...`), интерфейс находи по IP-подсети. Docker-шлюзам не доверяй. На роутерах `net.ipv4.ip_forward=1`.

| Сеть | Подсеть | Назначение |
|---|---|---|
| ext | 198.51.100.0/24 | «Интернет» |
| transit | 192.168.50.0/24 | общий коммутатор между МЭ, шлюзом ДМЗ, VPN, RADIUS |
| dmz | 192.168.100.0/24 | ДМЗ |
| intra | 192.168.200.0/24 | внутренняя сеть |
| wg | 10.8.0.0/24 | туннель WireGuard (не docker-сеть) |

| Узел | Адреса | Роль |
|---|---|---|
| fw-ext | ext .1, transit .1 | внешний МЭ, NAT/DNAT |
| gw-dmz | transit .2, dmz .1 | шлюз ДМЗ: МЭ + Suricata |
| vpn | transit .3, wg .1 | WireGuard-сервер |
| fw-int | transit .4, intra .1 | внутренний МЭ + Squid, RADIUS-клиент |
| radius | transit .5 | FreeRADIUS |
| web | dmz .10 | Apache + PHP, сайт-заглушка |
| ftp | dmz .11 | vsftpd (копии документов, бэкапы) |

| client | ext .10, wg .2 | легитимный удалённый пользователь |
| attacker | ext .66 | внешний нарушитель (nmap, curl, тесты XSS) |
| inet | ext .80 | «сайт в интернете» для проверки выхода АРМ |

Маршруты:
- fw-ext: 192.168.100.0/24 через .50.2; 192.168.200.0/24 через .50.4; 10.8.0.0/24 через .50.3.
- gw-dmz: default через .50.1; 10.8.0.0/24 через .50.3; 192.168.200.0/24 через .50.4.
- fw-int и vpn: default через .50.1; недостающие подсети через соседей по таблице.
- Хосты dmz/intra: default через свой шлюз (.1 в своей сети).
- Хосты ext: default на fw-ext (198.51.100.1). У attacker и client отдельный маршрут `192.168.0.0/16 via 198.51.100.1`. Так видно, что МЭ режет попытки достучаться до внутренних сетей.

## Политика МЭ, режим `protect` (по умолчанию)
Политика по умолчанию drop, плюс established/related. Каждое drop-правило имеет именованный `counter` (логи nft в контейнерах недоступны, нужны счётчики и `nft list ruleset`).
- fw-ext: из ext разрешить только tcp 80,443 на public 198.51.100.1 (DNAT → web) и udp 51820 (DNAT → vpn). ICMP из ext внутрь запрещён. Изнутри наружу разрешено только от fw-int (tcp 80,443, masquerade) для Squid. Всё остальное drop.
- gw-dmz: transit→dmz tcp 80,443 на web; tcp 21 (и диапазон пассивных портов) на ftp только из intra. dmz→intra только web→db tcp 5432. Остальное drop.
- fw-int: в intra из внешних зон только то, что разрешено явно (web→db 5432; VPN-клиенты 10.8.0.0/24 → arm1 tcp 22; ответы established). Из intra наружу: arm1→web 80/443, arm1→ftp 21, всё остальное в интернет только через Squid fw-int:3128. DNS и Kerberos внутри intra не фильтруются.
- Режим `audit`: правила ACL не применяются (всё forward accept), но маршрутизация, DNAT, IDS и логи работают. Переключение: `stand/scripts/mode.sh protect|audit` (идемпотентно, без перезапуска контейнеров).
Конкретные наборы правил по узлам продумай сам, но придерживайся этой политики и запиши итоговые правила в результаты.

## Структура `stand/`
- `docker-compose.yml`, `stand/nodes/<узел>/` (Dockerfile, конфиги), общий базовый образ `gis-base` (debian + iproute2, nftables, iputils-ping, curl, tcpdump, netcat-openbsd, dnsutils, procps).
- `stand/scripts/`: `up.sh`, `down.sh`, `mode.sh`, `shot.sh`, `shot-web.sh`, `check-*.sh`.
- `stand/secrets/`: ключи и пароли (в `.gitignore`).
- Если проект ещё не под git, сделай `git init` в `gis/`. Коммить после каждого этапа.

## Скрины
- `stand/scripts/shot.sh <имя> <команда…>`: выполняет команду, сохраняет реальный вывод в `results/screens/<имя>.txt` (первая строка вида `user@host:~$ команда`) и рендерит `results/screens/<имя>.png` в виде тёмного окна терминала (моноширинный шрифт с кириллицей, ширина около 100 колонок, длинные выводы обрезай осмысленно).
- `shot-web.sh`: скрин веб-страницы из контейнера `client` (headless chromium внутри контейнера), PNG кладёт в `results/screens/`.
- Имя скрина `NN-коротко.png`, где NN — номер этапа. `.txt` рядом оставляй всегда, он нужен для сверки.
- Зависимости для скринов ставь внутри `gis/` (venv) или в контейнерах. На хост ничего не ставь без вопроса.

## Шаблон `results/NN-название.md`
```
# Этап NN — название
## Цель
## Что сделано (5–10 строк)
## Конфигурация (ключевые фрагменты; полные файлы указаны путями в stand/)
## Проверка функционирования
### Проверка K — что проверяем
- Команда: `…`
- Ожидание: …
- Получили (реальный вывод): …
- Скрин: screens/NN-….png
- Итог: PASS/FAIL
## Отступления от схемы и причины
## Проблемы и как решили
```
Одна проверка — один скрин с реальной командой. Если проверка не прошла, пиши FAIL и разбор, а не подгоняй вывод.

## Критерий готовности стенда
`stand/scripts/up.sh` поднимает всё с нуля. `check-all.sh` (этап 06) проходит. Для каждого механизма (МЭ, IDS, VPN, домен/RADIUS, web/БД) есть проверка «до/после» или «разрешено/запрещено» со скрином.
